### 1. Overview

Multi-agent squads that combine several small models into role-specific collaborators are increasingly showing that, when well designed, they can outperform a single frontier model at problem solving.

But the more agents work in parallel, the harder it is for people to see the thought process each agent goes through to solve a problem. Existing AI interfaces flatten work that multiple agents perform at the same time into a single, linear conversation, so there's no way to tell how a squad is composed, or in what order and relationship each agent broke down and worked on the problem.

AFO (All Forward One) was built to solve this problem — when a user asks a question, it visualizes how a squad made up of a `Planner` and several specialized agents works through it, as a node-based graph that preserves the parallel structure.

Users can see the squad's composition at a glance, and interactively follow which order (vertical axis) and parallel relationship (horizontal axis) each agent ran in, along with the input it received and the output it produced.

I built this project with team Bean Noodles, made up of a designer, a frontend developer, a full-stack developer, and an AI developer. As the full-stack developer, I developed both the `React`-based client and the `FastAPI`-based server, worked on improving the squad's performance, and served as the point of contact with the Lablup staff along the way.

By researching different agent configurations, our team also recorded the 3rd-highest benchmark score among the 14 participating teams.

### 2. System Architecture

AFO works by taking a user's input, having the squad process it, and returning the result.

The squad consists of a `Planner` that analyzes the request and builds an execution plan, specialized agents such as `Coding Agent`, `Math Agent`, and `Generic Agent` for different domains, and the One Shot Prompt delivered to each agent. Tasks with no dependencies on each other are grouped into the same wave and run at the same time, and the agents' outputs are then summarized back into a single result.

| Service  | Role                                                                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client   | Takes the user's request, manages squads and sessions, and visualizes each wave of agents' reasoning as a node graph                                                 |
| Server   | Builds the squad's composition and execution plan, runs agents in parallel and summarizes their results, and manages authentication and session/conversation history |
| Database | Stores user authentication data along with squad and session/conversation history                                                                                    |

I built the client with `React`, `TypeScript`, and `Vite`. In the node graph, the vertical axis represents the order agents ran in (by wave), and the horizontal axis represents parallel execution within the same wave, so users can intuitively follow the squad's reasoning flow.

I built the server with `FastAPI` and `Python`, using `Supabase` as the database for authentication and for storing squads and conversation history.

### 3. Retrospective

While putting the squad together, I spent a lot of time researching different agent collaboration structures — Planner-Solver-Judge, Solver-Aggregator, and more — sketching candidate configurations by hand and comparing and validating them. Through this, I came to feel that how clearly you separate roles and prompts matters more for a squad's performance than simply adding more agents.

We had three models to choose from for our agents — Qwen, gpt-oss, and EXAONE — and after benchmarking a range of combinations, the configuration that used gpt-oss for every agent scored the highest.

While using Lablup's Backend.AI GO, I used Claude Code to figure out that changing the timeout value in the router settings broke the `/ai.backend.go/router_config.yaml` file. I reported this to the organizers, and the fix was included in a new release.

After building our squad to improve the performance of the agents provided by Lablup and FuriosaAI, I was also analyzing the logs and noticed that, judging by the timestamps, the agents appeared to be running serially rather than in parallel. After discussing it with the Lablup staff, we confirmed that the agents were in fact being processed in parallel and that the issue was in the logs themselves.

Building a visualization that lets users follow multiple agents running in parallel — not tediously, but in a way that's actually engaging — also turned out to be trickier than I expected. Before landing on the node graph structure, where the vertical axis represents order and the horizontal axis represents parallelism, I had to try and refine several different layouts.

Building both the `React` client and the `FastAPI` server let me build a product end to end for the first time — authentication, squad parsing, and near real-time graph playback all included. It also taught me not to just take the tools I'm given at face value, but to verify anything that looks off and work it out together with the people who provide them — and it gave me a lot to think about in terms of how to design a multi-agent system that people can actually trust and understand.
